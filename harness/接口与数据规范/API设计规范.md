# API 设计规范

本文档约束 HTTP API 的资源建模、路由声明、参数、响应和错误边界。数据结构细节以《数据结构与响应规范》为准。

## RESTful 原则

- API 以资源为中心建模。
- 路径表达资源层级，HTTP 方法表达操作语义。
- 常规 CRUD 不在路径中使用动词。
- 非资源动作必须是少数例外，并通过动作子资源表达。
- 不为单个页面或前端组件定制非资源化接口。

## 路由命名

- 路径使用小写短横线命名，例如 `/user-profiles`。
- 资源路径使用名词，不使用动词。
- 集合资源使用复数语义。
- 子资源通过层级表达，例如 `/users/{user_id}/sessions`。
- 登录态接口按 session 资源建模，例如 `POST /auth/session` 和 `DELETE /auth/session`。
- 系统级接口放在独立控制器中，例如 `/health`。
- 不在路径中暴露内部实现、数据库表名或第三方平台细节。

## HTTP 方法

- `GET`：查询资源，不产生业务副作用。
- `POST`：创建资源；无法资源化的动作作为少数例外。
- `PUT`：整体替换资源。
- `PATCH`：局部更新资源。
- `DELETE`：删除或停用资源。

无法自然映射到资源 CRUD 的动作，使用清晰的动作子资源，例如 `/tasks/{task_id}/cancellation`，避免 `/cancel-task` 这类动词路径。

## 路由声明

- controller 继承 `litestar.Controller`。
- 每个路由声明 `path`、`operation_id` 和 `summary`。
- `operation_id` 使用 `领域:动作` 格式，例如 `system:health`。
- controller 返回类型标注具体 `GenericResponse` 泛型。
- controller 不直接拼接响应字典。

## 参数规则

- 路径参数表达资源标识。
- 查询参数表达过滤、排序、分页和轻量开关。
- 请求体表达创建、更新或复杂操作载荷。
- 请求体和查询参数对外字段命名遵守《数据结构与响应规范》。
- 路径参数与路由占位符保持小写蛇形命名。
- 分页参数统一使用 `limit` 和 `offset`。
- `limit` 必须大于 0，`offset` 不得小于 0。
- 排序字段必须白名单约束，不直接信任外部字段名。

## 响应规则

- 成功响应统一使用 `GenericResponse`。
- 分页响应统一使用 `GenericResponse[Pagination]`。
- 对外字段默认使用驼峰命名。
- 响应中不暴露内部异常、连接串、密钥、栈信息和本地路径。
- 空结果列表返回空列表，不返回 `None`。

## 错误边界

- 业务错误由统一异常处理层转换。
- controller 不手工拼错误字典。
- 错误信息面向调用方表达可理解原因，不泄露内部实现。
- 需要稳定错误码时，错误码应按领域分组并保持向后兼容。
