# Git 项目管理规范

本文档约束分支、提交和 Git 元数据相关的项目管理流程。命令入口、测试和质量检查分别遵守《项目指令规范》和《测试规范》。

## 分支策略

- 开始新的里程碑、功能或较大改动前，先从当前基线创建独立功能分支。
- 不在主分支或长期共享分支上直接开发功能改动。
- 分支名应表达工作范围，优先使用 `feature/`、`fix/`、`docs/` 等前缀。
- 同一分支只承载同一里程碑或同一功能范围内的改动。
- 如果发现当前分支混入无关工作，应先拆分或暂停，避免继续扩大审查范围。

## 原子提交

- 将实现拆分为可审查的原子子任务，每个子任务只包含一个明确行为或文档目标。
- 每完成一个原子子任务，先执行与改动范围匹配的测试和质量检查，再提交。
- 每个原子子任务使用独立提交，避免把无关改动、格式化、重构和功能实现混在同一提交中。
- 提交信息应准确描述本次子任务结果，不使用无法追踪意图的笼统描述。
- 如果某个提交必须同时包含生产代码和测试，测试应只覆盖该提交引入或改变的行为。

## 执行环境限制

- 如果当前执行环境无法创建分支、运行必要服务或写入 Git 元数据，应停止提交动作并说明限制。
- 遇到 Git 元数据只读、Docker daemon 不可访问或必要本地服务不可用时，不伪造验证结论。
- 需要完整项目权限的分支、验证和提交动作，应在具备对应权限的环境中执行。
