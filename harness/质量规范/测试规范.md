# 测试规范

本文档约束测试组织、测试范围、测试数据、fixture 和质量门禁。测试应验证行为和防止回归，不追求无意义覆盖率。

## 目录结构

测试目录镜像 `src/aigc` 下的被测模块层级：

```text
tests/
  auth/
  controller/
  shared/
  base/
```

- 测试文件使用 `test_` 前缀。
- 测试函数名应描述行为。
- 不使用 `test_1`、`test_ok`、`test_case` 等无语义名称。
- 跨模块通用夹具放在 `tests/conftest.py`。
- 领域专用夹具放在对应测试目录的 `conftest.py`。

## 测试范围

按改动风险选择测试类型：

- schema：默认不单独测试。
- service：数据库边界、数据转换和异常路径。
- handler：业务流程、规则判断、跨能力编排和异常路径。
- controller：路由、状态码、响应包装、参数绑定。
- 数据库：模型映射、分页、查询条件、迁移兼容性。
- 配置：默认配置、文件加载、格式兼容。
- 回归：已修复缺陷的最小复现。

测试应限制为最小必要范围，优先覆盖关键业务流程和接口契约。共享基础能力、数据库、响应结构和配置加载的改动需要更完整覆盖；文案、注释或纯 schema 形状变更不需要新增测试。

## 编写规则

- 测试不依赖执行顺序。
- 测试不共享可变全局状态。
- 异步代码使用异步测试。
- 测试函数、夹具参数和测试替身应补齐必要类型标注。
- 外部网络调用必须替换为 mock、stub 或本地假实现。
- 数据库、Redis、文件系统等外部资源必须使用隔离夹具。
- 测试阶段数据库使用临时 SQLite，不连接本地或生产数据库。
- 测试阶段 Redis 使用内存模式，不要求真实 Redis 服务。
- API 测试使用 Litestar 自带测试工具，不直接启动网络服务。
- 测试用例默认按被测行为组织；需要定义测试路由或视图时，优先使用 CBV，CBV 无法覆盖目标时才使用 FBV。
- 能通过 SQLite 夹具构造数据的场景优先使用真实库表和数据；无法稳定构造时才 mock。
- 时间相关测试使用固定时间。
- 随机值测试固定种子或断言稳定属性。
- 断言应验证业务结果，不只验证函数没有报错。
- 优先测试公共行为，不为覆盖率测试私有实现细节。

## Fixture

- 公共 fixture 放在 `tests/conftest.py` 或对应测试目录的 `conftest.py`。
- 只在多个测试复用时抽取 fixture。
- fixture 名称表达提供的资源或状态。
- fixture 不隐藏关键断言。
- 涉及资源创建的 fixture 必须清理资源。
- 领域专用 fixture 放在领域测试目录，不放到全局。
- 测试配置应覆盖 `Config.get()`，避免读取真实 `config.yaml`。
- 通用数据库 fixture 负责建表、清表或销毁临时库。
- API 测试 app 只用于 controller 测试，并只装配被测路由和必要依赖。

## 测试数据

- 使用最小必要数据构造场景。
- 敏感信息使用明显假值。
- 时间字段使用带时区的固定 `datetime`。
- ID、邮箱、名称等字段使用可读值。
- 排序或分页测试的数据应能体现顺序。
- 不复用生产配置中的真实连接串、令牌或账号。
- 测试用户和密码使用明显假值；需要验证密码逻辑时走真实写库和认证路径。

## 依赖规则

- 测试夹具需要的运行依赖必须写入项目依赖或测试依赖。
- 不在测试中通过可选本机服务弥补缺失依赖。

## 质量门禁

常规代码变更至少执行：

```bash
make test
make lint
```

涉及类型、共享抽象、数据库或响应结构时，额外执行：

```bash
make type-check
make coverage
```

涉及文档构建时，执行：

```bash
make docs-build
```

- 功能开发按原子子任务提交时，每个子任务提交前都必须完成与该子任务风险匹配的验证。
- 验证范围至少覆盖本次子任务直接影响的测试；当影响共享抽象、数据库、响应结构、配置或跨模块契约时，扩大到对应质量门禁。
- 如果子任务只改文档，不强制执行代码测试，但应执行适用的文档校验；无法执行时说明原因。
- 无法执行校验时，应说明原因和剩余风险。
